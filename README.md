# ChatBox 项目说明与使用教程

ChatBox 当前处于项目初始化阶段。仓库已经连接 GitHub，并建立了项目规则、中文说明书和 AI 开发交接文档；目前还没有应用源代码、可运行程序、业务功能、依赖清单或部署脚本。

**因此，下载这个仓库目前会得到项目文档和许可证，暂时不能启动一个聊天工具或微信机器人。** 本地文件夹名称为 `WeChat aibox`，这个名称不能作为微信接入、AI 对话或其他功能已经实现的依据。产品目标和技术方案都需要后续开发轮次明确。

本说明书同时服务两类读者：第一次接触项目的使用者，可以按教程查看、下载和更新项目；准备二次开发的程序员，可以从当前状态、目录职责、修改影响和开发流程了解哪些内容已经成立、哪些内容尚待设计。

## 3. 完全不懂 Git 时，可以先这样理解

Git 用来记录文件的不同版本。每次“提交”（`commit`）相当于给一组文件改动保存一个可追溯的版本；“推送”（`push`）把本地已有的提交上传到 GitHub；“拉取”（`pull`）把 GitHub 上的新提交下载并更新到本地。

这三件事有区别：保存文件不会自动提交，提交不会自动上传，上传也不表示程序已经经过运行验证。本项目要求 AI 在每轮实际开发完成必要验证和文档更新后自动提交并推送，这是开发规则，需要实际执行命令才能完成。

`origin` 是此项目给远程仓库起的名称；`main` 是当前本地分支；`origin/main` 是 Git 在本地保存的远端主分支状态。后者需要通过 `git fetch` 或 `git pull` 刷新，不能只看旧记录就判断 GitHub 此刻一定没有新变化。

下面的命令在 Windows PowerShell 中运行。代码块里的每一行是一条命令，按顺序执行即可；不要把终端输出当成下一条命令粘贴。

### 3.0 第一次使用：检查或安装 Git

在 Windows 开始菜单搜索并打开 PowerShell，输入：

```powershell
git --version
```

如果看到 `git version ...`，说明 Git 已经可用，直接继续第 3.1 或 3.2 节。若提示无法识别 `git`，按下面步骤安装：

1. 打开 [Git 官方 Windows 安装页面](https://git-scm.com/install/windows)。在 `Standalone Installer` 区域选择安装程序：通常的 x64 电脑选择 `x64 Setup`，ARM 电脑选择 `ARM64 Setup`；电脑类型可在 Windows 设置的“系统 → 关于 → 系统类型”查看。
2. 双击下载的安装程序，按向导完成安装。第一次使用可保留默认选项；安装过程出现系统授权提示时，确认运行的是刚从官方页面下载的安装程序。
3. 安装完成后关闭并重新打开 PowerShell，再运行 `git --version`。显示版本号后再执行后续下载命令。若使用开发工具的内置终端，也需要重新打开终端，必要时重开该开发工具。

也可以按该官方页面提供的方式，在已支持 `winget` 的电脑上执行：

```powershell
winget install --id Git.Git -e --source winget
```

若提示找不到 `winget`，使用上面的安装程序方法即可。这里提供安装说明，不会自动在你的电脑上安装软件。

### 3.1 已经在当前主开发电脑上：直接打开现有仓库

当前项目已经位于 `D:\开发\WeChat aibox`，不要在这个已有项目目录里再次执行 `git clone`。

打开 PowerShell 后执行：

```powershell
Set-Location -LiteralPath 'D:\开发\WeChat aibox'
git --version
git status
git remote -v
git branch -vv
```

各命令的作用与正常结果：

1. `Set-Location` 切换到项目文件夹；路径里的空格由引号保护。
2. `git --version` 显示 Git 版本，说明命令可用。如果提示找不到 `git`，先按第 3.0 节安装并重新打开 PowerShell。
3. `git status` 显示当前分支和未提交改动。工作区干净时通常会出现 `nothing to commit, working tree clean`。
4. `git remote -v` 中的 `origin` 应指向 `https://github.com/wraaaaaa/ChatBox.git`。
5. `git branch -vv` 的当前分支前面有 `*`，应为 `main`，并显示它跟踪 `origin/main`。

如果结果与上述目标不一致，保留现有文件，先根据实际 Git 状态处理问题。不要为“重来一遍”而删除 `.git` 或项目文件。

### 3.2 换一台电脑：下载到一个全新的目录

前提是电脑上能够执行 Git 命令，并且所选父目录已经存在。以下示例把仓库下载成 `D:\开发\ChatBox`，要求这个目标目录尚不存在；它与当前主开发窗口使用的目录是两个独立的工作副本。

```powershell
Set-Location -LiteralPath 'D:\开发'
git clone https://github.com/wraaaaaa/ChatBox.git ChatBox
Set-Location -LiteralPath 'D:\开发\ChatBox'
git status
git remote -v
```

`git clone` 会创建 `ChatBox` 文件夹、下载文件，并建立 Git 版本记录。下载完成后，先阅读三份项目文档。不同电脑上的本地改动不会实时共享，需要通过提交、推送和拉取同步。

如果 `D:\开发` 不存在，可选一个自己已经建立的文件夹，并相应修改示例路径。如果目标 `ChatBox` 文件夹已经存在，先确认它是什么内容；不要把现有文件夹删除来迎合示例命令。

只想阅读说明书的人也可以直接打开 [GitHub 项目页面](https://github.com/wraaaaaa/ChatBox)，点击 Markdown 文件查看，无须启动应用。

### 3.3 更新一个已有工作副本

先进入自己的项目目录，检查本地是否有未提交改动：

```powershell
Set-Location -LiteralPath 'D:\开发\WeChat aibox'
git status
git branch -vv
```

确认工作区干净、当前为 `main` 且跟踪 `origin/main` 后执行：

```powershell
git pull --ff-only
git status
git log -5 --oneline
```

`git pull --ff-only` 只接受可以直接接上的远程更新。如果本地和远端已经产生不同的提交，它会停止并提示无法快进，便于先检查差异。`git log -5 --oneline` 显示最近五条提交，帮助确认取到了什么版本。

如果 `git status` 显示自己正在修改文件，先处理这些改动再更新。如果出现分支分叉、冲突或登录失败，记录终端实际提示并处理原因，不要使用强制推送或丢弃文件来跳过问题。

### 3.4 判断提交是否真的上传

在 Git 命令成功完成后，可执行：

```powershell
git fetch origin
git rev-list --left-right --count HEAD...origin/main
git status
```

在当前 `main` 分支上，第二条命令返回 `0 0` 表示本地提交与刚获取的远端 `main` 没有差异。第一项非零表示本地有远端没有的提交，第二项非零表示远端有本地没有的提交。还可以在 GitHub 项目页面核对最新提交及文件内容。

这个核对证明的是版本同步情况；未来出现应用代码后，程序能否运行仍需要另外验证。

## 5. 文件目录与实现原理

### 5.1 当前目录

```text
WeChat aibox/
├── .git/           Git 的本地版本记录与仓库信息
├── AGENTS.md       项目规则、开发进度和恢复工作的入口
├── README.md       中文使用说明与人类二次开发说明
├── VIBECODING.md   AI 开发交接材料
└── LICENSE         现有许可证原文
```

`.git` 是 Git 管理的数据目录，不能当成应用源代码手工修改。当前没有 `src`、前后端入口、数据库模型、服务接口、配置解析器、测试集或依赖文件；本说明书不会用假想目录替代它们。

### 5.2 当前已经成立的工作原理

当前项目的工作链路是：开发者读取规则和进度 → 核对仓库实际状态 → 修改授权范围内的文件 → 验证修改 → 同步三份文档 → 创建 Git 提交 → 推送至 `origin` → 核对远端结果。

三份 Markdown 文件之间存在说明关系：`AGENTS.md` 规定开发过程需要怎样执行，`README.md` 解释人类现在可以怎样使用和修改项目，`VIBECODING.md` 保存其他 AI 开发者需要接手的事实与关联。它们都是文档，不会自行启动程序，也没有文件监听器根据文档内容自动执行 Git。

目前没有业务调用链可供讲解。未来新增模块时，必须先从实际代码梳理“从哪个入口开始、经过哪些函数或服务、读写哪些配置与数据、最终返回什么结果”，再把关联写进 README 和交接文档。

### 5.3 每个新功能应记录哪些实现细节

为了让使用者和二次开发者都能理解，后续每个功能至少应覆盖以下内容：

1. **功能目的与实现状态**：解决什么问题，已经完成到什么程度，有哪些暂时不支持的情况。
2. **使用入口与教程**：如何找到入口，逐步怎么操作，输入什么，正常输出或界面变化是什么。
3. **代码位置与调用关系**：真实文件路径、关键函数、上下游模块，入口如何抵达结果。
4. **配置与修改效果**：在哪改、允许的值、默认值、修改后改变什么、是否需要重启，以及会影响哪些其他功能。
5. **数据与外部依赖**：读取和保存什么数据，存在哪里，依赖哪些服务，服务失败时如何处理。
6. **验证与恢复方法**：实际执行过哪些检查，正常标志是什么，出错如何定位，如何恢复到先前可用状态。

新增 API、数据库或第三方接入时，还要写明真实接口与数据格式、兼容边界、错误处理方式，以及修改它们会影响的调用者。需要配置账号、密码或令牌时，文档解释字段用途和填写位置，示例使用占位值。

## 6. 修改某处会带来什么效果

当前仓库只包含文档与许可证，现有修改影响如下：

| 修改位置 | 直接效果 | 需要一起核对的内容 |
| --- | --- | --- |
| `AGENTS.md` 的固定规则 | 改变后续开发者需要遵守的协作方式 | README 的开发流程、VIBECODING 的交接约束；用户明确制定的规则不能擅自改写 |
| `AGENTS.md` 的进度记录 | 改变恢复工作时对已完成与待办的认识 | README 的状态表和进度、VIBECODING 的当前状态与下一步 |
| `README.md` 的功能或教程 | 改变使用者对功能、启动和操作方式的理解 | 实际仓库是否支持该描述，VIBECODING 的实现事实是否一致 |
| `VIBECODING.md` 的模块关联或验证状态 | 改变接手 AI 的开发依据 | 真实文件与调用链、AGENTS 的进度、README 的实现原理 |
| 文件改名或移动 | 原有文档链接可能失效，规则入口可能无法被工具发现 | 三份文档中的引用、目录映射、工具读取方式 |
| `LICENSE` | 改变仓库提供的许可文本 | 本轮不修改；查看许可时阅读原文 |
| Git 远程或分支配置 | 后续拉取和推送的目标可能改变 | 当前 `origin` 地址、`main` 与 `origin/main` 的对应关系 |

未来出现代码后，这张表必须继续扩充到真实模块、配置和数据结构。例如实际实现了某项配置时，要明确它的作用范围和生效条件；不能在还没有配置项时凭空写出默认值。

## 7. 人类程序员和 AI 应如何开展下一轮开发

### 7.1 开始之前

1. 阅读根目录 `AGENTS.md`，确认当前规则与进度；再阅读本文件和 `VIBECODING.md`。
2. 核对 Git 分支、远程、未提交改动和最近提交，识别工作目录中的真实文件。
3. 明确本轮用户授权的目标。当前产品功能尚未定义，先把具体需求变成可以验证的行为，再决定合适的技术方案。
4. 如果仓库以后已有代码，先梳理受影响的入口、调用者、配置和数据，再动手修改。

### 7.2 修改与验证

按本轮目标实现最小必要改动。把既有未提交改动与本轮改动识别清楚，保留用户文件。检查修改产生的直接效果以及会受影响的关联行为，并在文档里记录实际测试结果。

当前是文档初始化，验证重点是内容是否与仓库一致、三份文档是否互相一致、引用是否有效、Git 差异是否符合预期。未来添加应用代码后，需要补充对应的编译、启动、功能和关联行为检查；不能以本轮文档检查替代未来应用测试。

### 7.3 更新文档、提交并推送

本项目已经明确授权：**每轮实际开发完成后自动执行 Git 提交与推送，并详细跟进这三份 Markdown。** 不需要每轮重新询问是否推送；如果命令失败，应记录真实原因和待恢复步骤，不能把未上传的变化报告成远端已更新。

在核对修改范围之后，文档初始化这一轮的提交示例是：

```powershell
git diff --check
git status --short
git add AGENTS.md README.md VIBECODING.md
git diff --cached --stat
git commit -m "docs: establish project rules and Chinese documentation"
git push origin main
```

上述 `git add` 只选择三份文档；未来有代码修改时，需要根据本轮实际范围追加对应文件。提交前检查暂存内容，提交说明应准确概括那一轮的改动。推送后再按第 3.4 节核对结果。

提交和推送记录以 Git 的实际输出、历史和远端状态为准。不要把某个提交自己的 SHA 写回同一个提交来作为证明；工作区有文档并不等于它们已经提交或已经上传。

## 8. 常见问题

**下载后为什么没有可启动的程序？**

因为当前仓库只有项目文档和许可证，业务应用尚未开始实现。这不是少执行了某个安装命令。

**是否已经能够连接微信或大模型？**

目前没有这样的代码和功能。名称不能证明接入已经完成，未来以实际功能表、代码和验证记录为准。

**切换到另一个 AI，怎么让它接上进度？**

先给它最新的 `VIBECODING.md`。文档提供现状、关联和开发边界；进入同一仓库后，还要读取 `AGENTS.md`、README 和真实代码来核对。如果只给历史版本的交接文件，它无法知道此后出现的新改动。

**上下文压缩后规则还在吗？**

规则文件仍保存在仓库中。恢复开发时需要重新读取它，不依赖模型对压缩前聊天内容的记忆。工具不会自动发现规则文件时，需主动提供 `AGENTS.md`。

**“每轮自动 push”为什么不是保存文件后马上出现在 GitHub？**

这是 AI 开发流程中的执行规则。开发完成后要实际提交再推送；没有后台同步服务。推送还需要远程访问和可用的写入权限。

**`git push` 失败后怎么办？**

保留本地文件和提交，查看实际错误。权限或认证问题需要修复对应环境；远端比本地更新时，需要获取并检查远端变化，再解决分叉或冲突。不能用强制推送覆盖他人的提交来消除报错。处理完成后重试并核对远端。

**看到 “nothing to commit” 是失败吗？**

通常表示没有新的文件改动可以提交。如果这一轮只是咨询且没有修改项目文件，这是正常情况；如果本来应有改动，需确认修改保存在哪个目录、是否已经提交，或是否被忽略。

**文档能保证修改后不会出现任何错误吗？**

文档能提供真实关联、约束和检查方法，降低遗漏风险；是否可用还取决于实际实现和验证。接手者应沿真实调用链检查影响，并明确未测部分，不能把“读过文档”当成应用已经验证通过。
